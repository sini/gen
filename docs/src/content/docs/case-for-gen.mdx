---
title: The Case for gen
description: What gen changes for people who run Nix configuration, and where the project stands today.
---

Nix describes a whole machine as code: its packages, services, users and settings. Teams use it to
run anything from one workstation to thousands of servers from a single repository. As that
repository grows, most of the effort moves from the features themselves to the wiring between them.
Someone has to remember which machine gets which feature, which feature needs which other one, and
which value each file expects to be handed.

gen is a set of Nix libraries that turn that wiring into a graph. Machines, users and features
become nodes, and the relationships between them become edges that software can check, query and
explain. The sections below describe what that changes.

## Relationships you can ask about

In a typical Nix repository, relationships are stored in the shape of the code. A feature reaches a
machine because a file sits in its `imports` list. A value reaches a module because three other
modules pass it along. A setting applies because an `mkIf` somewhere tests the right condition. None
of those relationships is written down as a fact. Move an entry, rename an argument or reorder a
list, and the relationship changes with no error to say so.

gen records each relationship as an edge in a graph. "Which machines run monitoring?" and "which
users can log in to this database server?" become queries, and the answer is computed from the
edges. One machine and a thousand machines are the same query over a bigger graph.

## Write a feature once

A feature in gen, called an aspect, is written once and shared by every machine that uses it. When
the feature needs something about the machine it lands on, such as its address or its users, it
asks for the machine as an argument and gen passes it in. The same SSH feature gives each machine
its own list of allowed users, with no copy per machine.

Features can include other features. A monitoring feature that needs SSH says so once, and every
machine that runs monitoring gets SSH as well. [Aspects](/features/aspects/) shows this in code.

## Built on settled results

gen's main mechanisms come from published research, each with its proofs already worked out.
Resolving what a machine sees is name resolution over a scope graph. Rules that add relationships
are a logic program with stratified negation, solved for its well-founded model, so a rule that
depends on its own negation is reported as undefined. Rebuilding after an edit is demand-driven
recomputation with early cutoff, so its result always equals a full rebuild. The [Reading
List](/reference/reading-list/) and [Papers](/reference/papers/) pages link each result to the part
of gen that uses it.

## Every piece of configuration has an identity

gen gives every machine, user and feature an identity computed from its content. Two things with
the same content get the same identity, every time. That one property pays off in three places.

**Reuse and speed.** gen recognises work it has already done. After an edit, it reuses every result
the edit did not affect, and the output is identical to a full rebuild. In gen's benchmarks,
re-evaluating six edits against earlier work costs a quarter of evaluating each from scratch. On a
real set of three NixOS machines, an edit to one machine skips two thirds of the composition work
for all three.
The [benchmarks](/benchmarks/) page has the figures and how they are measured.

**Errors that point at the cause.** Every declared option records which file set
it, at which priority, and which other definitions it replaced. The next step builds on
identity: reporting a failure against the machine and feature that caused it, where plain Nix
reports a stack of evaluation steps. The [Roadmap](/roadmap/) tracks that work.

**Seeing the whole configuration.** gen can load the graph and the results of its rules into one
set of facts. You can query those facts with SQL, ask why a relationship exists and get the rules
that produced it, and draw the graph as a diagram. Interactive graph tools are planned.

## Works with the module systems you already use

gen's module system follows the same rules as the one in nixpkgs for everything the two share, and
a test suite compares the two on every change. It also accepts nixpkgs' own option types: run with
real nixpkgs `lib.types` and `mkOption`, it produces byte-identical output on gen's benchmark
corpus, so existing modules and custom types can come along during a port. [Coming From the Module
System](/guides/from-module-system/) shows both.

A feature's NixOS content is an ordinary NixOS module, evaluated by a NixOS system builder at the
end. gen passes values into modules written for other evaluators through the same argument
injection it uses for its own. The longer-term goal is to offer gen's extensions to modules written
for any framework.

## Checked on three Nix implementations

Every gen library's test suite runs on each push under upstream Nix, Determinate Nix and Lix. The
[Trust](/trust/) page lists each guarantee gen makes and the check behind it.

## Where it stands

gen is pre-release: the libraries ship and are tested on every push, their APIs are still changing,
and the first framework built on the full toolkit is in progress. The [Roadmap](/roadmap/) says what
comes next.
